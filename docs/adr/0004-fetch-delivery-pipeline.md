# Fetch → filter → dedup → deliver pipeline

The job pipeline runs **in-process** on the gateway (Bun) via a `cron` schedule (`*/15 * * * *`, ADR-0002 `Feature.schedule`), not a separate worker or Redis/`pg_cron`. This minimizes deploy complexity (single `pg` Pool, no extra auth) and keeps the `schedule` contract upgradeable to `Bun.spawn` later. Each tick selects active `subscriptions` and **groups by fingerprint** `hash(source,keywords,location,geoId,distance,filters)` so identical filters across 5 subscriptions incur 1 LinkedIn guest fetch, then fan-out to matching subs. Each fingerprint fetches ≤3 pages (`start` offset 0,10,20, 10 cards/page, 2s jitter per request per research-01/02) and stops on 200+empty `<li>`; capped concurrency avoids burst.

Retry is tiered: 429/999 → exponential backoff `2^attempt` + jitter, 3 retries; Cloudflare `__cf_bm` 403/302 → 1 UA-rotated retry then 60m circuit-breaker per fingerprint; 5xx → 1 retry; logged with `feature`/`fingerprint`. Delivery is **insert-seen-first**: `INSERT INTO seen_jobs ... ON CONFLICT DO NOTHING RETURNING` per `(subscription_id,source,external_id)` (ADR-0003), only on `inserted` does `channel.send(embed)`. This gives at-most-once per subscription without distributed lock; with >1 replica, `pg_try_advisory_xact_lock(hashtext(fingerprint))` serializes fetches. The 15-minute tick is globally owned (`bot_config.poll_interval_minutes` override), not per-subscription timers, respecting LinkedIn's 2s cadence and avoiding thundering herd.
