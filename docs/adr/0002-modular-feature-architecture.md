# Modular feature architecture: core + defineFeature registry

With Bun+Elysia+discord.js chosen (ADR-0001), we split the bot into **core** (shared runtime: client, registry, loader, DB, config, logger, Elysia server) and **features** (`src/features/<feature>/`), each self-contained (`index.ts`, `commands/`, `events/`, `schedule.ts`, `schema.ts`, `adapter/`). Features never import each other; `src/app.ts` boots Elysia + discord.js, `src/index.ts` is the entrypoint. Flat `src/` (not `apps/packages` workspaces) is sufficient for MVP and preserves modularity — adding a second feature does not touch core.

Contract is `defineFeature({ name, description, commands, events, schedule, schema })` in `src/core/feature.ts`; loader discovers features via `Glob('../features/*/index.ts')`, validates, and exposes `register()` (REST) and `start()` (events/schedule). Slash commands are centrally registered via single `REST.put(Routes.applicationCommands)`, and `interactionCreate` dispatches by name; same for `client.on(event)`. Failure isolation is per-feature `try/catch` + supervisor logging/metric, schedule isolated by `Promise.catch`, top-level `unhandledRejection` handler keeps the process alive; schedule initially runs in-process via `cron` lib but the `schedule` contract allows promotion to `Bun.spawn` worker later without feature changes. Elysia lives in `src/core/server.ts` (`/health`, `/metrics`), features may extend it via `feature.server?.(app)`; Drizzle schema is re-exported at `src/db/schema.ts`, migrations generated to `drizzle/` via `drizzle-kit` on `DATABASE_URL_UNPOOLED`, and `migrate()` runs at boot before REST registration.
