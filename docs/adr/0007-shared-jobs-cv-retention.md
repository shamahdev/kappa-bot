# Shared jobs table, CV profiles, and 14-day retention

Amends ADR-0003: the schema grows 5 → 7 tables. New `jobs` holds one row per real posting, deduped by `(source, external_id)` across all subscriptions and keywords — the shared listing (url/title/company/location) plus the cached `ai_summary`, computed once per posting (Groq cost) and reused by every card render. New `cv_profiles` holds one CV per Discord user, keyed by user id with no `users` FK (Discord-only users have no `users` row) and deleted explicitly on account delete. `seen_jobs` stays per-subscription (composite unique and insert-seen-first per ADR-0003/0004 unchanged) and gains a nullable `job_id` FK (`onDelete:cascade`, new index) plus `match_score`/`match_reason`, written only for DM-scope cards against the subscriber's CV — guild rows stay NULL, so the personal-only boundary holds at the data layer. The `jobs` listing columns are first-sighting-wins; rows with no `seen_jobs` reference are pruned by the existing TTL pass. Migration 0009 backfills `jobs` from `seen_jobs` snapshots, so no history is lost.

Retention default drops 30 → 14 days for new subscriptions (Neon storage cost; existing rows keep their stored value, per-row override via `/jobs config` and the dashboard unchanged). This deliberately diverges from ADR-0003's "30 days matches LinkedIn's `f_TPR` max window": retention is a storage TTL, not a search window, and re-delivery after expiry was already documented behavior.

Explicitly deferred: caching the raw posting description (the detail fetch stays live for fresh closed/salary status), scoring multi-item digest lists (reply-by-number and single cards score; lists stay title-only for Groq cost), and DB-level length caps (the 1500-char summary cap lives in app code).
